  一句话定位

  双 Agent(Planner ↔ Executor)跑在本地 mlx 端点(上下文窗口 ~64k、不支持原生 tool_calls)上解 CTF 逆向题。上下文策略的核心目标(代码注释里标为
  §6):让上下文永远概括"当前全部进度",却始终远低于 64k——靠的是把"进度"和"细节全文"分离到不同存储层。

  分层记忆结构(ContextManager,context.py:41)

  这是整套设计的地基。四层,信息从"永久常驻"到"可丢弃"递减:

  ┌─────────────┬──────────────────────────────────────────────────────────────────────┬─────────────┬────────────────────────────────────────────────────┐
  │     层      │                                 内容                                 │    存哪     │                      生命周期                      │
  ├─────────────┼──────────────────────────────────────────────────────────────────────┼─────────────┼────────────────────────────────────────────────────┤
  │ Working     │ 目标 + 已确认事实 + ⚠️ 用户实时提示                                   │ 上下文置顶  │ 常驻                                               │
  │ Memory      │                                                                      │             │                                                    │ 
  ├─────────────┼──────────────────────────────────────────────────────────────────────┼─────────────┼────────────────────────────────────────────────────┤
  │ 结构化台账  │ 4                                                                    │ 上下文常驻  │ 常驻、空间有界(每类去重+尾部截断,如函数图留最近    │
  │ ledger      │ 类:func_map(函数地图)/reads(已读字节)/attempts(解题尝试)/scans(概况) │             │ 50、尝试留 20)                                     │ 
  ├─────────────┼──────────────────────────────────────────────────────────────────────┼─────────────┼────────────────────────────────────────────────────┤
  │ 历史窗口    │ 最近 window 步的原始往返全文(近处细节)                               │ 上下文      │ 滑动,更早的由台账代表                              │ 
  ├─────────────┼──────────────────────────────────────────────────────────────────────┼─────────────┼────────────────────────────────────────────────────┤
  │ 外部记忆    │ 每次工具调用的全文(反编译/字节等)                                    │ SQLite      │ 永久,靠 artifact#id 按需 recall                    │
  │             │                                                                      │ (store.py)  │                                                    │
  └─────────────┴──────────────────────────────────────────────────────────────────────┴─────────────┴────────────────────────────────────────────────────┘

  关键理念:"远处只留骨架,近处才留细节"——早期步骤滑出窗口后,不丢失,而是被台账的结构化条目代表。

  每步 messages 如何拼(context.py:239 build_messages)

  [system_prompt]
  + [task + Working Memory 块]   ← 稳定前缀
  + [最近 window 步的 assistant/user 往返]

  稳定前缀刻意放在前面,是为了本地端点的 KV cache 复用(§6.4):system + 台账这段跨步基本不变,只有尾部窗口在滚动。

  三重"去噪/压缩"(这是最容易忽略但很关键的一环)

  1. 观察压缩(_context_view context.py:163):反编译伪代码截 3500 字、disasm 截 4000 字进上下文;超 big_threshold=800 的全文落 SQLite,上下文里替换成 _artifact_id +
  "需要重看用 recall"。
  2. 模型输出压缩(_compress_output react_executor.py:161):模型自己的 rambling 不原样进窗口,只抽 THOUGHT 首段(≤280 字)+ 规范化的
  ACTION。注释写得很直白——否则"模型的循环推理会当 assistant_text 喂回给自己,既撑爆上下文又强化打转"。
  3. 强制去注释(_strip_py_comments react_executor.py:146):用 tokenize 剥掉 run_python 代码里的所有注释再执行+入上下文(模型不听"禁注释",就程序化强制)。

  外部记忆 = 对二进制做 RAG + 工具缓存(store.py)

  同一张 artifacts 表干两件事:
  - RAG:大输出进库,上下文只留摘要+id,recall(artifact_id) 取回全文;
  - 工具缓存:find_cached(run_id, tool, args) 命中就直接返回,避免重复跑 IDA 分析(react_executor.py:319 对只读 IDA 工具查缓存)。
  - 还有 contains() 用于反假阳性:FINAL 的 flag 必须在某条全文里真实出现过。

  跨轮承接(Planner↔Executor 多轮,graph/*)

  build.py 组装 Planner → Executor →(replan/done/fail) 的 LangGraph。四样东西跨轮共享,让"重规划"便宜且不重复:

  1. 共享 SQLite 缓存(同一 db_path)→ replan 时 IDA 分析命中缓存,20 轮才跑得动;
  2. 台账跨轮重建(load_prior context.py:184)→ 新一轮 executor 从库里重放此前所有工具调用,继承全部发现;
  3. 进展总结回传(_summarize_round react_executor.py:286)→ 每轮结束让模型自己写"搞懂的算法/取到的数据/试过什么为何失败/卡在哪",连同 ledger_text() 一起喂给下一轮
  Planner(nodes.py:71);
  4. 共享 progress/deadline → stuck 与时间预算跨轮累计,不是每轮各吃满。

  上下文健康度守护(反空转 / 反卡死,§11)

  - stuck 检测(react_executor.py:420):超 stuck_seconds(默认 600s)无"新进展"→ 提前判失败。"新进展"定义很严——台账长出新条目(grew),或产出 flag
  样候选;纯反复反编译/乱码尝试不算(react_executor.py:128 _is_progress)。
  - 重复检测:同一 action 连续 ≥2 次、或同一工具 ≥4 次 → 注入"换完全不同思路"的系统提示。
  - max_tokens=2048(react_executor.py:439):实测硬题上模型会用满 8192 空谈到截断,把想调的 ACTION 挤没了,故砍到 2048 逼它尽早吐 ACTION。
  - 截断容错:半截 JSON(bad_parse)不整段进窗口,只回喂纠错提示。

  触发式知识注入(knowledge.py)

  一份知识库三种用法,都围绕上下文预算:
  - checklist() → 常驻精简清单进 system prompt;
  - inject() → 检测到征兆当场贴 detail(如花指令 _junk_signs、VM _vm_signs),seen 集合保证每条每轮只注一次,避免刷屏;
  - recall() → 卡住时按 topic 主动取详细解法(recall_knowledge 工具)。

  默认参数一览(solve_one.py:16)

  window=4 · max_steps=20/轮 · max_replan=19(20 轮) · stuck_seconds=600 · big_threshold=800 · max_tokens(executor 2048 / planner 900 / summary 800)。

  设计取舍的主线:本地弱端点(无原生 tool_call、窗口小、thinking 会卡死、易 rambling)逼出了这套"结构化台账常驻 + 全文外置 SQLite + 激进压缩输入输出 +
  严格进展判据"的组合——把有限的上下文预算全部让给"当前进度概览 + 最近细节",其余一律外置可召回。
